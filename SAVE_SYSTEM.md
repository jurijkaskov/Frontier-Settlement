# Документация системы сохранений: Frontier Settlement (Пункт 34)

## 1. Архитектурный обзор (Architecture Overview)

Система сохранений спроектирована по стандартам **Clean Architecture** и встроена в существующий слой данных без дублирования источников правды.

```
       [ UI / Presentation ]
                 │
                 ▼
       [ GameViewModel ]
                 │
                 ▼
     [ GameStateRepository ] ───► [ GameResumeDestinationResolver ]
                 │
     [ GameSaveCoordinator ] ───► Mutex-защита и синхронизация
                 │
                 ├────────────────────────┬────────────────────────┐
                 ▼                        ▼                        ▼
     [ GameSaveSerializer ]     [ GameSaveMigrator ]     [ GameStateNormalizer ]
                 │                        │                        │
         Moshi + CRC32            v0 -> v1 -> vN             Инварианты & Clamps
                 │
                 ▼
     [ FileGameSaveDataSource ] (or InMemory for tests)
                 │
                 ├─► Staging (.tmp) + Atomic Rename
                 └─► Rotation (autosave.json -> autosave_backup.json)
```

## 3. Анализ подхода к данным: DTO vs Domain Model

* **Выбранный подход**: Прямая чистая сериализация доменного `GameState` с помощью кастомных Moshi-адаптеров для полиморфных запечатанных интерфейсов (`TechEffect`, `EventRequirement`, `QuestRequirement`, `QuestFailureCondition`) в связке с легким мета-заголовком `SaveMetadata` и `GameSaveMigrator`.
* **Обоснование**:
  1. `GameState` в проекте уже спроектирован как чистая, иммутабельная структура данных (`data class` без ссылок на Android Context, View или CoroutineScope).
  2. Все статические каталоги и объемные шаблоны (контент-паки, таблицы лута, описания мобов) разделены через data-driven реестр `GameContentRegistry`. В `GameState` сохраняются только идентификаторы инстансов и их динамические состояния, что обеспечивает компактность файла сохранения (< 50 КБ).
  3. Для полиморфных типов реализованы строгие адаптеры с явным полем `"type"`, что исключает уязвимости рефлексии и обеспечивает совместимость.

## 4. Политика автосохранений (Autosave & Milestones)

Автосохранения подразделяются на два типа:
1. **Критические точки (Immediate Critical Saves)** — принудительная запись без ожидания:
   - Завершение игрового дня (`endDay()`).
   - Окончание тактического боя (победа/поражение/отступление).
   - Возвращение экспедиции на базу и разгрузка каравана.
   - Сдача сюжетного задания и получение наград.
   - Изучение ключевой технологии.
2. **Фоновые сохранения (Debounced Routine Saves)**:
   - Регулярные промежуточные сохранения во время исследования карты пустошей.

---

## 5. Управление слотами (Multi-Slot Management)

Поддерживаются следующие фиксированные слоты:
* `autosave` — Основное циклическое автосохранение.
* `autosave_backup` — Резервная копия предыдущего успешного автосохранения.
* `manual_1` — Ручной слот №1.
* `manual_2` — Ручной слот №2.
* `manual_3` — Ручной слот №3.

Игрок может переименовывать ручные слоты, перезаписывать их с подтверждением через диалоговое окно и удалять ненужные сохранения.

---

## 6. Атомарная запись на диск (Staged Atomic Writes)

Запись файла в `FileGameSaveDataSource` гарантирует защиту от сбоев питания:
1. Данные сериализуются в строку JSON.
2. Производится запись во временный файл `save_<slotId>.json.tmp`.
3. Выполняется вызов `fos.flush()` и `fos.fd.sync()` для физического сброса буферов на диск.
4. Проверяется размер и корректность `.tmp` файла.
5. Для `autosave` текущий файл переносится в `save_autosave_backup.json`.
6. Выполняется атомарное переименование `.tmp` в целевой файл `save_<slotId>.json`.

---

## 7. Ротация резервных копий и аварийное восстановление (Backup & Fallback)

Если основной файл `autosave.json` поврежден (например, повреждена структура JSON или не совпадает контрольная сумма):
1. `FileGameSaveDataSource` обнаруживает ошибку чтения.
2. Автоматически проверяется наличие `save_autosave_backup.json`.
3. Если бэкап валиден, система прозрачно загружает данные из резервной копии и возвращает `SaveLoadResult.Success(..., loadedFromBackup = true)`.
4. В UI отображается информационное уведомление о восстановлении данных.

---

## 8. Проверка целостности и CRC32 Контрольные суммы (Checksum & Validation)

* При сохранении вычисляется CRC32 хеш-код от JSON-представления `GameState`.
* При загрузке CRC32 сверяется. При несовпадении генерируется предупреждение в системный лог `GameLogger` и задействуется механизм аварийного отката.

---

## 9. Конвейер миграций схемы (Migration Pipeline)

* При загрузке `GameSaveMigrator` считывает поле `schemaVersion`.
* Если `schemaVersion < CURRENT_SAVE_SCHEMA_VERSION`, последовательно применяются зарегистрированные шаги `SaveMigration` (`v0 -> v1 -> v2`).
* Если `schemaVersion > CURRENT_SAVE_SCHEMA_VERSION`, загрузка отклоняется с понятным сообщением `SaveLoadResult.UnsupportedNewerVersion` во избежание повреждения данных новой версии игры.

---

## 10. Возобновление игры и приоритеты маршрутизации (Resume Destination Resolver)

При загрузке сохранения `GameResumeDestinationResolver` анализирует состояние и определяет правильный экран:
1. **Тактический бой** (`activeCombat != null`) ➔ Маршрут `"combat"`
2. **Неразрешенное событие экспедиции** (`activeExpedition.currentEvent != null`) ➔ Маршрут `"expedition_live"`
3. **Несобранный лут экспедиции** (`pendingLoot.isNotEmpty()`) ➔ Маршрут `"expedition_live"`
4. **Прибытие на локацию** (`phase == AT_LOCATION`) ➔ Маршрут `"arrival"`
5. **Активное исследование** (`phase == EXPLORING`) ➔ Маршрут `"expedition_live"`
6. **Движение по карте** (`isCurrentlyTraveling == true`) ➔ Маршрут `"map"`
7. **Поселение по умолчанию** ➔ Маршрут `"settlement"`

---

## 11. Нормализация состояния (GameStateNormalizer)

Для устранения мелких некорректностей без потери прогресса перед загрузкой запускается `GameStateNormalizer`:
* Ограничение (clamp) показателей здоровья (HP) и очков действия (AP) в пределах `0..max`.
* Принудительное обнуление отрицательных ресурсов: `max(0, amount)`.
* Удаление несуществующих ID персонажей из состава отряда.
* Сброс отслеживания удаленного задания (`trackedQuestId`).

## 12. Тестирование и верификация (Testing Strategy)

В проекте реализован комплекс модульных и интеграционных тестов (`SaveSystemTest.kt`):
- Полный цикл сериализации/десериализации (Round-Trip).
- Контроль CRC32 и защита от битых файлов.
- Атомарность записи `.tmp` и удаление временных файлов.
- Ротация бэкапов `autosave` ➔ `backup` ➔ авто-восстановление.
- Миграция схемы v0 ➔ v1.
- Восстановление боевого состояния, параметров бойцов, баффов и кулдаунов.
- Восстановление активных экспедиций, событий и несобранных трофеев.
- Нормализация поврежденных данных.
- Потокобезопасность `Mutex` в `GameSaveCoordinator` при параллельных запросах на сохранение.
